# Encoding routes toward a sub-100,000-vbyte publication

Question: can purely algebraic setup and a different access structure reduce
creation plus spending below 100,000 vB for an arbitrary later-chosen 256-byte
proof, while preserving precommitted point labels and public recovery?

No construction meeting all of those conditions has been established here.
The calculations below isolate what a successful construction must change.
They are `locally-reproduced` arithmetic and `inspected` structural arguments;
deployment is `unclassified`. They do not assert a universal impossibility.

## Exact bounds for explicit independent tables

For an ideal single global pool of N independent candidates with exactly t
revelations, capacity is `binomial(N,t)`. An arbitrary 256-byte value needs
at least `2^2048` codewords. We minimize the indicated linear byte cost over
all integers satisfying that constraint. This is an optimistic relaxation:
verification, most transaction framing, signature guards, resource bounds,
pool splitting and usually selectors are omitted.

| Restricted representation | Relaxed byte cost | Best N / t | Minimum bytes |
|---|---|---:|---:|
| Embedded 33-byte verification keys; 71-byte signatures | `34N + 72t` | 2,297 / 714 | **129,506** |
| HASH160 key table; 71-byte signatures; omit selectors | `21N + 106t` | 2,714 / 592 | **119,746** |
| Same, one selector byte per revelation | `21N + 107t` | 2,714 / 592 | **120,338** |
| Embedded keys; optimistically 65-byte signatures | `34N + 66t` | 2,259 / 733 | **125,184** |
| HASH160 table; 65-byte signatures; omit selectors | `21N + 100t` | 2,664 / 602 | **116,144** |
| HASH160 table; even freely available 58-byte signatures | `21N + 93t` | 2,609 / 614 | **111,891** |
| Individually funded P2SH locks, spend only selected ones | `32N + 191.25t` | 2,785 / 579 | **199,853.75** |

Every byte in these legacy tables/openings is a stripped transaction byte.
For the selective-spending row, the 32-byte creation output and complete
191-byte input assume a 76-byte redeem script and 71-byte signature; the extra
quarter vbyte accounts for an empty witness vector alongside a SegWit helper.
Unspent outputs are still paid for. This row also optimistically assumes a
sound mechanism binding the publication's total cardinality, which separate
UTXOs do not provide by themselves.

The same capacity bound applies to a sound antichain with at most t revealed
labels per codeword, for `t <= N/2`. To see this, consider a uniformly random
ordering of all N labels and its chain of prefix sets. An antichain meets each
chain at most once. A particular k-element set appears with probability
`1/binomial(N,k)`, so the sum of those probabilities over all codewords is at
most one. Since `binomial(N,k) <= binomial(N,t)` for every permitted k, there
can be at most `binomial(N,t)` codewords. Thus simply allowing variable
revelation counts does not evade the worst-case explicit-table bound.

The minimum candidate count is 2,054, since the largest fixed-weight layer with
2,053 candidates has fewer than `2^2048` elements. Merely moving a larger table
to bare legacy Script cannot evade these accounting bounds. Bare scripts may
remove the P2SH 520-byte limit but still have the 10,000-byte script and
201-operation limits; custom bare scripts also have different relay-policy
requirements.

[The executable calculation](sub100-encoding.py) uses exact Python integer
binomial coefficients and binary search for each minimal t. It enumerates
`2048 <= N <= 10000`; at larger N even the least expensive table alone costs
more than every incumbent. These minima apply to the stated explicit-table,
fixed-weight family, not to implicit algebraic candidate sets, truncated
commitments, correlated witness encodings or a different protocol.


## Correlated labels: count closures, not bases

If candidate label scalars are public linear combinations of secret basis
scalars, revealing several labels makes every label in their linear span
available. Two witnesses spanning the same subspace are therefore not two
independent publications. Encoding the order of a basis, or which spanning
tree of a component was revealed, creates alternatives requiring no new
secret. The message must be associated with the closure itself, and accepted
closures must form an antichain under derivability.

Correlations alone do not increase the number of closures generated by exactly
t selections from an explicit N-element list: there are at most `binomial(N,t)`
such selections, and closure can only merge them. Their potential benefit is
representing many candidate points implicitly using fewer committed parameters.
That requires both an inexpensive Script membership check and an honest way to
prepare openings for the implicit family.

A promising abstract family is a bipartite graph. Commit endpoint keys `P_i`
and `Q_j`, and define a candidate target `T_ij = P_i + Q_j`. A common signature
under a selected pair gives `t_ij = -2C/r` when the existing size guard rules
out mixed `r+n` lifts. Each target can be computed from public endpoint points,
so a complete a-by-b grid would encode ab labels using only a+b public keys.

Selecting exactly one edge for each left endpoint is a useful closed access
structure: the selected graph is a union of stars, each with one right endpoint.
Disclosing those sums does not, generically, reveal an edge to another star.
There are `b^a` such assignments, without requiring distinct right endpoints.
Perfect matchings are another closed family with `a!` choices for a square
grid. This avoids the spanning-tree ambiguity, assuming the endpoint secrets
have no additional public linear relations.

The hard part is **honest setup**. For every usable edge, the holder needs a
known nonce k satisfying

```text
x(kG) mod n = -2C / (p_i + q_j) mod n.
```

Knowing endpoint private scalars does not give that nonce. A spanning tree can
be prepared freely by choosing a nonce and solving for a new endpoint, but it
has only V-1 usable edges for V vertices. Every added cycle imposes a further
scalar relation among nonce-derived values. We do not have an efficient dense
family satisfying those relations.

As an intentionally conditional illustration, a complete 20-by-20 graph has
`20!` perfect matchings (about 61 bits) using 40 endpoint keys and 20 selected
signatures. The keys and signatures alone cost 2,800 bytes per pool before
verification, permutation handling, transaction framing or resource checks.
This is close enough to the target to motivate an implicit-family search, but
it is **not a usable construction**: preparing all 400 openings is unresolved,
and verification overhead cannot be ignored. A one-edge-per-left-endpoint
assignment offers more capacity but has the same opening-generation problem.

## A heuristic obstacle to nonce-table graph preprocessing

Let S contain the nonce-derived scalars `-2C/x(kG)` from at most `2^b` sampled
known nonces. Treating those scalars as random, a connected endpoint graph with
V vertices and E required edges has roughly

```text
2^[256(V-1) - (256-b)E]
```

labelings whose every edge sum belongs to S. For `b=64`, the expected-count
threshold is `E <= (4/3)(V-1)`. A dense 20-by-20 graph is vastly outside that
range. This is a random-set heuristic, not a lower bound against specialized
algebraic structure or adaptive attacks on the secp256k1 x-coordinate map.
It explains why ordinary birthday preprocessing is unlikely to produce the
needed density under a total `2^64` work budget.

A single eight-edge cycle can reduce to an eight-list sum relation, but gains
only one usable edge over a spanning tree. Dense graphs need many independent
cycle relations. Long-cycle generalized-birthday tricks therefore must solve
both the aggregate work budget and endpoint reuse; counting only the cost of
one isolated cycle is misleading.

## Excluded shortcuts

- Choosing the committed points after the proof is known would turn the proof
  into a few fixed scalar revelations, but violates the later-chosen-message
  requirement of precommitted BitVM labels.
- An ordinary ECDSA signing key can grind nonce bits to carry public payload
  bytes cheaply. It does not reveal the predetermined independent point labels
  needed here; a fresh signature can encode the same digit with a different
  point.
- Reusing a small point pool independently in many positions exposes its union
  and permits alternative encodings from already revealed secrets.
- A hash-to-subset signature with the proof supplied separately is not the same
  as guaranteed point-label recovery. It would need a binding and unavoidable
  validation mechanism tying those separately supplied bytes to the chosen
  labels; that mechanism's cost and semantics cannot be omitted.
- Free variable cardinality saves bytes arithmetically, but deleting optional
  records can leave a Bitcoin-valid yet undecodable publication. The CSV
  variant has a separate, explicit sequence-authorization requirement; it does
  not remove that requirement by merely including a helper input.
