# R14: exactly one coordinate orbit when all three r values fit hash signatures

Question: can a three-point endomorphism orbit, with each signature supplied
by a 32-byte SHA256 result, provide the small authenticated query h cheaply?

There is **exactly one x-coordinate orbit**, up to rotation, for which all
three nonzero ECDSA r values are at most `2^191-1`. It has h=2. Its point
coordinates lift with both signs of y, giving two oriented point orbits.
Two of its r values differ by one. This is an exact finite result, not a
sample or a claim about all endomorphism uses.

It also narrows this particular hash-signature proposal sharply: h is
constant, and a fresh uniform 32-byte hash must hit one of three fixed r
encodings. The probability for even one such hash, allowing all 256 flag
bytes and every fitting positive s, is `32895/2^192`, approximately
`2^-176.9944`. At most `2^64` distinct ideal-oracle queries have success
probability at most about `2^-112.9944`. No general SHA256 lower bound or
general covenant impossibility is inferred.

Evidence: `locally-reproduced`; deployment: `unclassified`. The
[Python](r14_orbit_observable.py) and [JSON](r14_orbit_observable.json)
contain exact integer certificates, coordinates and DER boundaries.
No Script implementation, hint interface, signature hash preimage, or nonce
discrete logarithm is produced here; consequently there is no locking-script,
witness, stack or transaction metric to report for a new primitive.

## Why the entire search becomes a tiny lattice box

Let `Delta=p-n`, `M=2^191-1`. A 32-byte canonical DER signature including its
flag has integer lengths `nr+ns=25`. Since s is nonzero, `nr<=24`, hence
`r<=M`. This is a necessary condition; it does not presume that Script can
parse r.

For a genuine endomorphism orbit, use ordinary representatives xi in
`[1,p-1]`, and write `xi=ri+ai*n`, with ai either 0 or 1. By the
[R13 identity](r13_orbit_query.md),

```
sum(xi) = h*p,       h=1 or 2,
sum(ri) = h*Delta + (h-sum(ai))*n.
```

Now `0<sum(ri)<=3M<n` and `0<h*Delta<n`. Therefore

```
sum(ai)=h,           sum(ri)=h*Delta.
```

For h=1 exactly two coordinates are unwrapped. Choose the unique consecutive
ordered pair of those coordinates along the beta orbit, u and v. They obey

```
1<=u,v<=Delta-1,     v=beta*u mod p,     u+v<Delta.
```

The third coordinate is `p-u-v`. Conversely, every liftable pair with these
properties gives such an h=1 orbit.

For h=2 exactly two coordinates are wrapped. Choose their consecutive
ordered pair x and x'. Put `u=p-x`, `v=p-x'`. Since the corresponding r
values are positive, again

```
1<=u,v<=Delta-1,     v=beta*u mod p.
```

The original coordinate orbit is `p-u,p-v,u+v`. Here `u+v<2Delta<n`, so the
third coordinate is indeed unwrapped. No triangle restriction is required
for this h=2 case. Rotating the original orbit or selecting the inverse
endomorphism does not produce a missing coordinate set: beta fixes an
orientation, and the consecutive equal-wrap pair is unique in that order.

Both cases are thus exhausted by the same lattice box, not a 191-bit scan.

## Exact enumeration certificate

All solutions of `v=beta*u mod p` form the lattice generated by `(1,beta)`
and `(0,p)`. A reduced basis is

```
a = (-303414439467246543595250775667605759171,
      -64502973549206556628585045361533709078)
b = ( 64502973549206556628585045361533709078,
     -367917413016453100223835821029139468249).
```

The determinant is exactly p; each column satisfies the congruence.
For any point `(u,v)` in the closed box `[1,Delta-1]^2`, the inverse matrix
gives its integer coefficients as

```
ca = (b_y*u-b_x*v)/p,
cb = (-a_y*u+a_x*v)/p.
```

Extrema of these affine functions occur at the four corners. Exact ceiling
and floor evaluation forces `ca=-1` and `cb in {-1,0}`. Testing those two
coefficient pairs leaves exactly one box point:

```
u = 303414439467246543595250775667605759171
v =  64502973549206556628585045361533709078.
```

The code independently cross-checks this direct coefficient enumeration
against R11's exact line/rectangle iterator. In this case `u+v<Delta`.
The h=1 coordinates `u,v,p-u-v` do not lift to secp256k1: all three have
quadratic-nonresidue curve right-hand sides. The h=2 coordinates
`p-u,p-v,u+v` do lift. Their r values, in that order, are

```
r0 = 129005947098413113257170090723067418155
r1 = 367917413016453100223835821029139468248
r2 = 367917413016453100223835821029139468249.
```

They have bit lengths 127, 129 and 129. The code verifies the same even y
and `lambda*Ri=R(i+1)` exactly, as well as `sum(ri)=2Delta` and `r2-r1=1`.
Negating y produces the second point orbit, leaving r and h unchanged.
The first r has two available x lifts; the second and third each have one.
The unused lift is not silently treated as another endomorphism orbit.

## Exact hash-format count

The first r uses 16 DER integer bytes and the other two use 17. At total
signature size 32 including the flag, this leaves respectively 9 and 8
bytes for the s integer. For integer-byte length k>=2, the positive
canonical interval is

```
2^(8k-9) <= s <= 2^(8k-1)-1,
count = 255*2^(8k-9).
```

This includes encodings with a required sign-padding zero and excludes
unnecessary padding. All these s values are below n/2. Including every
flag, the three disjoint r cases contain

```
256*255*(2^63+2*2^55) = 32895*2^64
```

possible 32-byte strings, out of `2^256`. The implementation checks both
endpoints of each s interval, the shorter encoding immediately below it,
and the longer encoding immediately above it. It supplies no hash preimage.

For a fresh ideal SHA256 oracle this gives the stated probability. The
union bound includes all distinct setup and online queries, including
adaptive selection of inputs: the target output set is fixed by the exact
curve constants and format. It already upper-bounds success for the weaker
event that **one** query has a suitable r, without requiring all three
signatures, native contexts, orbit enforcement or output binding. Restricting
flags can only reduce the target set.

## What remains constructive

The one-unit r difference and the known relative point multipliers are real
new algebraic data. Their usefulness outside the all-three-hash-signature
proposal remains open. They do not reveal the individual nonce logarithms.
For example, in R13's shared antipodal-key-pair interface, a transition from
r1 to r2 still requires the native digest ratio `z2/z1=r2/r1`, a full scalar
condition. Two identical SINGLE-bug contexts cannot satisfy it.

An actionable extension must give an executed native predicate binding the
points or the one-unit difference, and a cheaper intended-output witness
algorithm whose full setup is counted. The existing short-value identity
alone supplies neither. Full-length signatures linked by a different hash
interface are expressly outside the 32-byte enumeration result.
