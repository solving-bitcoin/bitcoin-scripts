# Checked u32 per-byte population counts

`arithmetic::u32::popcount::u32_byte_popcounts` consumes one u32 represented
by four numeric byte limbs and returns each byte's population count. It shares
the checked 256-entry table used by `u32_popcount`, but preserves the four lane
results instead of adding them.

- **Input:** `byte[0] | byte[1] | byte[2] | byte[3]`, most significant byte
  first, with the least significant byte on top.
- **Output:** four numeric ScriptNums in `0..=8`, in the same byte order; the
  least significant byte's count is on top.
- **Evidence:** `locally-reproduced` by boundary, representative-word, and
  malformed-byte rejection tests, plus a strict metric fixture.
- **Representative result:** 452 locking-script bytes, 13 serialized witness
  bytes across four `0xff` data items, 262 combined stack items, and no hints.
  The fragment contains 168 static non-push opcodes; this is not an executed
  opcode or deployment claim.
- **Execution class:** `unclassified`. The strict local executor uses a
  tapscript context and the combined stack limit; Bitcoin Core consensus and
  relay policy have not been differentially tested.

The 256-item table is generated by the locking script and removed before the
four results are returned. Compared with `u32_popcount`, this variant saves the
three final addition bytes and retains lane-local information. A caller that
only needs the total should use `u32_popcount`; adding the four returned values
reconstructs that total at the cost of those additions.

This is a fragment, so callers still provide any terminal predicate, clean-stack
rule, and byte-unique ScriptNum binding needed by their protocol.
